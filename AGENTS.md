# Agent instructions

## VERY IMPORTANT: demos and exercises specification

[Demos_and_Exercises_Specification.md](./Demos_and_Exercises_Specification.md)
is the authoritative requirements document for this project. Its rules are
mandatory, not optional guidance.

- Before changing demos, exercises, shared code, configuration, infrastructure,
  slides or related documentation, read the global requirements and all sections
  relevant to the change, including acceptance criteria and the Section 3
  slide/code cohesion contract.
- Preserve every applicable requirement. Do not silently relax, bypass or break
  a rule for convenience, simplification, refactoring or personal preference.
  Follow the specification's distinction between MUST, MUST NOT and SHOULD.
- Keep code, slides, names, commands and runbooks consistent. When changing code
  shown on a slide, update the slide in the same change and perform the required
  cohesion checks.
- If a compliant approach is possible, use it. Propose an exception only when
  there is a concrete, defensible reason, such as conflicting requirements or a
  technical blocker that cannot reasonably be resolved within the specification.
- Before making any such exception, stop and ask the user for explicit approval.
  Identify the exact rule, explain why an exception makes sense, describe its
  impact and present a compliant alternative when available. Do not ask to break
  rules without a meaningful reason.
- Approval applies only to the specific exception discussed; it is not permission
  to disregard other requirements. Update the specification and affected
  documentation to reflect an approved requirement change.
- Validate changes against the relevant acceptance criteria and required checks.
  If a required check or artifact is unavailable, report the blocker explicitly;
  do not claim compliance or completion without verification.
